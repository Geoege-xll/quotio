# CPA 启动后的菜单栏额度同步修复

日期：2026-10-15。

## 问题与原因

CPA 启动后，菜单栏已经切换为 CPA 当前凭据目录，但额度可能仍是未知；在账号页手动刷新后才出现数值。

`initializeFullMode()` 先运行本地 `refreshQuotasUnified()`，记录全局额度节流时间。原启动流程随后两次调用 `refreshData()`；该入口只有到达轮询时间才派生额度刷新任务。因此目录已切到 CPA，而 CPA 的精确凭据额度没有首轮读取。菜单栏不会用本地同邮箱的其他凭据冒充结果，所以显示未知。页面手动刷新绕过轮询节流，才补齐缺失快照。手动刷新频率没有自动轮询，尤其容易持续出现此现象。

## 本次修改

生产变更仅在 `Shared/Accounts/ViewModels/QuotaViewModel+ProxyLifecycle.swift`：

1. 启动仍依次执行首次目录读取、同步本地禁用状态、再次目录读取。两次目录读取使用 `refreshData(refreshQuotas: false)`，避免同时隐式派生额度任务。
2. 禁用状态同步完成后，在原启动任务中明确等待 `refreshAllQuotas(waitForAvailability: true)`，绕过旧来源的轮询节流。即使刷新频率为手动，也完成这一次启动初始化；之后的周期设置照旧。
3. 若已有刷新占用槽位，复用原等待机制。取消、停止、重启、切换模式或替换客户端后，流水线检查来源并退出；额度获取器继续使用原提交校验。
4. 首轮取数通过原额度发布和通知入口更新菜单栏，不依赖账号页面打开。完成后继续原预热、升级检查和隧道启动流程。

未修改账号映射、CPA API、额度解析、通知装配、界面布局或用户配置；没有新增存储、任务句柄或第二个采集消费者，没有放宽 `private(set)`。

## 必要验证

Debug 构建成功，14 项定向回归全部通过，0 失败、0 跳过；未运行全量测试。

新增 `ProxyStartupQuotaSyncTests` 六项，覆盖：

- 本地刚刷新后的节流期，以及手动／十分钟频率下的启动初始化；真实离线 CPA 返回剩余 55%，同一菜单栏快照和原通知均获得更新。
- 直接调用生产首轮入口，遇到已占用批量槽位时等待，取消不释放其他刷新持有的槽位。
- 首轮单提供商取数等待原槽位释放后继续，并更新菜单栏。
- 目录请求挂起时取消、停止、重启、换客户端和换模式，禁止旧流水线继续取数或提交目录。
- CPA 额度迟到时，不能向重启后的会话提交旧额度。
- CPA 主额度失败时保留未知及失败标记，不借用本地其他账号。

另外定向执行原槽位协调两项、菜单账号映射三项和启动协调器三项，保留同邮箱隔离、重复启动合并及取消传播。

测试使用临时偏好、空凭据目录和 URLProtocol 离线响应，只改变并恢复代理内存运行状态。成功路径的测试门面将批量额度一步限定为真实 Claude 单提供商刷新，目录、精确 auth_index 请求、解析、槽位和菜单通知仍为生产实现；生产批量等待另有直接覆盖。没有启停真实 CPA，也没有实测用户账号的在线额度或运行中菜单 UI。
